# Explicit Run and text extensions

Run configurations are versioned data with stable UUID, user-chosen name, an absolute executable path and separate arguments. Reading/importing configuration never launches it. The user selects a saved entry in Run to execute it. `{file}`, `{directory}` and `{selection}` expand only when each is an entire argument; spaces, quotes, substitutions and metacharacters remain argument bytes.

The selection is passed exactly as selected and nothing is inserted before it. A selection that begins with `-` is therefore read by the tool as an option. Where the tool supports it, put `--` or the tool's own pattern flag (for example `-e` for grep) before `{selection}` in the saved arguments. A selection that contains a NUL character or is longer than 1 MiB cannot be an argument; the run is refused with an error that says so, and a text extension, which receives the selection on stdin, is the way to process such text. A command without a `{selection}` argument is not affected by what is selected.

Run > Manage Commands… shows every saved command as the version 1 library in indented JSON: name, executable, arguments, `shellMode` and `extensionMode`. Editing an entry changes the command, removing an entry deletes it, and keeping `id` keeps its identity. Saving validates the whole library and never runs anything. If `RunCommands.json` could not be read, Configure, Manage and Add Sample all refuse to save, so the unreadable file is left as it is. The menu shows the executable name beside the command name. On the first run, TextTank displays the full argument list, execution mode and working directory. Cancel leaves the previous result available. TextTank remembers the command after it launches. Editing the saved command prompts again. The private RunApprovals directory stores one SHA-256 digest per command identity. Each saved command's menu item has a tooltip with what it executes: the executable and arguments, prefixed `shell:` or `text extension:` where that applies and cut at 300 characters.

A command starts in the folder of the saved document. For an unsaved document, or when that folder no longer exists, it starts in the home folder. The environment is inherited from TextTank unchanged and unfiltered; when TextTank is opened from Finder that is the small environment launchd provides, not the one a terminal has.

Intentional shell mode is an explicit checkbox and uses `/bin/zsh -c`. Document variables are not interpolated into shell code. Shell mode is not used by extensions.

Version 1 text extensions receive UTF-8 selected text, or the document when no selection exists, through stdin. They return UTF-8 on stdout, diagnostics on stderr, and exit zero for success. The result is previewed, then applied only by a separate explicit button while document revision, selection and writable lifetime still match. Applying is one Undo. A newer preview invalidates older Apply controls. Invalid UTF-8, nonzero exit, cancellation and truncated output cannot be applied.

The included sample uses the system `/usr/bin/tr a-z A-Z` to uppercase ASCII. It is an actual process/stdio integration, not a Unicode case-conversion promise. The user can save the sample from Run and invoke it on synthetic text. Windows DLL binary compatibility and the complete Notepad++ plugin message/event API are not implemented by this limited interface.

Runs use an isolated process group, 4 MiB input/output bounds and a fixed 30-second timeout. Cancel signals that group, escalates termination, closes bounded nonblocking pipe readers and leaves document contents unchanged. Descendants are cleaned up when the scoped run finishes, including those that redirect output; daemonization is not a supported run mode. Cleanup is by process group: a descendant that leaves the group with `setsid()` or `setpgid()` is not reached and keeps running.

Quitting TextTank stops a command that is still running: once the quit is committed (after any unsaved-documents review), the group is signalled as for Cancel and TextTank waits up to one second for it to go. A crash or a forced quit cannot do this.

The result window says why the run ended, and each cause has its own text: finished; cancelled; stopped at the time limit; stopped at the 4 MiB output limit; or finished while a background process it started still held the output open, in which case that process is stopped and the output may be incomplete. Only a finished run can be applied. If the exit status could not be collected the window says "No exit status" and the result is treated as a failure, never as exit 0. External programs can perform their own filesystem/network effects, so only explicitly configured, trusted programs should be invoked. No program is run by opening a document, macro, workflow, session or settings file.
